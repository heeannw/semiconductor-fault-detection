# AMHS 개념 정리 & 이 프로젝트의 매핑

SK하이닉스 AMHS 직무 면접 준비용으로 작성. AMHS(Automated Material Handling System)는 반도체 fab 내에서
웨이퍼(FOUP)를 공정 장비 사이로 자동 운반하는 물류 시스템이다. `amhs/` 모듈과 `notebooks/07~09`는 이 개념들을
직접 구현하며 이해도를 다진 결과물이다. 디스패칭 정책은 스스로 만들어본 것이지만, 그 설계가 실제 연구/업계
방향과 어디서 겹치고 어디서 갈리는지는 §8 참고 문헌에서 밝혀둔다.

## 1. 핵심 용어

| 용어 | 설명 |
|---|---|
| **FOUP** (Front Opening Unified Pod) | 웨이퍼 25장을 담는 밀폐 카세트. AMHS가 반송하는 기본 단위 — "웨이퍼 하나하나"가 아니라 FOUP 단위로 움직인다. |
| **OHT** (Overhead Hoist Transport) | 천장 레일을 따라 움직이며 FOUP를 집어 운반하는 무인 반송 차량. 300mm 웨이퍼 fab에서 사실상 표준 반송 수단. |
| **Stocker** | FOUP를 임시 보관하는 자동창고(버퍼). 공정 장비 간 처리 속도 차이를 흡수해 라인이 멈추지 않게 한다. 용량이 다 차면 다운스트림의 정체가 업스트림으로 번진다(**back-pressure**). |
| **Bay** | 같은 종류의 공정 장비들이 모여 있는 구역. **Intrabay**(bay 내부 반송) vs **Interbay**(bay 간 반송)로 계층이 나뉜다. |
| **MCS** (Material Control System) | AMHS의 두뇌. MES로부터 반송 요청(어떤 FOUP를 어디서 어디로)을 받아 어떤 OHT에게 배정할지 결정한다. |
| **Dispatching** | MCS가 반송 요청을 차량에 배정하는 규칙/알고리즘. 목표는 반송 시간 최소화 + 장비 유휴시간 최소화 + 혼잡 방지. |
| **Cycle Time** | 반송 요청 발생부터 FOUP가 목적지에 도착할 때까지 걸린 시간. AMHS의 핵심 KPI. |
| **Vehicle Utilization** | 전체 시간 중 OHT가 실제로 FOUP를 운반 중인(또는 이동 중인) 비율. 너무 낮으면 차량 과잉 투자, 너무 높으면 병목. |
| **Congestion** | 특정 구간에 반송 요청/차량이 몰려 대기시간이 급증하는 상태. 레이아웃 설계와 디스패칭 품질이 직접 영향을 준다. |
| **SECS/GEM** | 반도체 장비-소프트웨어 간 표준 통신 프로토콜. MES/MCS/장비가 이 프로토콜로 반송 요청·완료를 주고받는다. |
| **Hot Lot** | 납기가 급하거나 문제를 조기 확인해야 하는 긴급 로트. 일반 로트보다 반송/공정에서 우선순위를 받는다. |

## 2. 왜 AMHS가 중요한가

- 웨이퍼가 공정 장비에 도착하지 못하면 장비가 아무리 빨라도 놀게 된다 — **AMHS는 fab 전체 처리량(throughput)의 실질적 상한선**을 정한다.
- OHT 한 대가 고장 나면 그 구간 전체가 정체되고, 정체는 인접 구간으로 번진다(도미노 효과) — 그래서 **차량 예지보전**이 단순 "고장 예측"을 넘어 라인 전체 리스크 관리다.
- 디스패칭 알고리즘 하나 바꾸는 것만으로 동일한 차량 대수로 처리량을 크게 바꿀 수 있어, **알고리즘/최적화 역량**이 설비 투자보다 저렴하게 성과를 낼 수 있는 영역이다.

## 3. 이 프로젝트에서 다루는 것

| AMHS 개념 | 프로젝트 구현 |
|---|---|
| 레이아웃(공정 스테이션 + 반송 네트워크) | `amhs/layout.py` — 기존 `simulator/`의 8대 공정을 노드로 재사용, 반송 거리/속도 추가 |
| 스토커(입력 버퍼) + back-pressure | `amhs/simulation.py` — 설비 `simpy.Resource`의 대기열 길이를 스토커 점유량으로 사용, 용량 초과 시 OHT가 드롭오프를 미루고 대기 |
| OHT 반송 시뮬레이션 + Cycle Time/가동률/혼잡 측정 | `amhs/simulation.py` (SimPy 이산사건 시뮬레이션), `notebooks/07_amhs_dispatch_simulation.ipynb` |
| 디스패칭 알고리즘 비교 | 같은 노트북에서 최근접 차량 / FCFS / 구역기반 / 예측 기반 정책을 동일 시나리오로 비교, 대시보드에서 실시간 실행도 가능 |
| Hot Lot(긴급 로트) 우선순위 | `amhs/simulation.py` — 디스패처가 대기 중인 반송 요청을 FIFO가 아니라 hot lot 우선으로 고른다. 경쟁이 있을 때만 효과가 있다는 것까지 확인 |
| 반송 지연·혼잡 예측 | `notebooks/08_amhs_delay_prediction.ipynb` — 시뮬레이션 로그로 XGBoost 회귀/분류, `amhs/predictive.py`로 실시간 디스패칭에도 연결 |
| 차량 예지보전 | `amhs/vehicle_health_simulator.py` + `notebooks/09_amhs_predictive_maintenance.ipynb` — SECOM에서 쓴 IF+XGBoost 앙상블 파이프라인을 OHT 차량 센서(모터 전류, 진동, 온도)에 재적용, `amhs/maintenance.py`로 시뮬레이션에도 피드백 |
| 대시보드 연동 | `backend/app/main.py`의 `POST /api/amhs/simulate`가 SimPy 시뮬레이션을 즉시 실행(< 1초) — React 대시보드 "AMHS 물류" 화면에서 디스패칭 정책 비교/차량 대수 민감도를 버튼 클릭으로 실시간 확인 |

SECOM/공정 시뮬레이터 파트는 **FDC(Fault Detection and Classification)** — "웨이퍼가 불량인가"를 다뤘다면,
AMHS 파트는 **그 웨이퍼가 공정 장비까지 제때 도착하는가**를 다룬다. 같은 fab을 서로 다른 두 축(품질 vs 물류)에서
바라본 셈이라, 두 파트를 하나의 레포에 함께 두는 게 자연스럽다.

## 4. 시뮬레이션 결과 (`notebooks/07_amhs_dispatch_simulation.ipynb`)

> **버그 하나 잡은 이야기**: 스토커를 처음엔 별도의 `simpy.Store`로 만들어서 FOUP가 도착하자마자
> 그 자리에서 바로 자기 자신을 꺼내가게(get) 했다. 그랬더니 버퍼가 사실상 한 번도 안 채워지는
> 구조가 되어(즉시 자기소비), 어떤 부하를 줘도 최대 큐 길이가 계속 1로만 나왔다 — back-pressure가
> 전혀 관측되지 않는 상태였던 것. 원인은 "FOUP이 설비 앞에서 대기하는 것"과 "누군가 스토커에서
> 꺼내가는 것"을 별개의 이벤트로 분리해둔 설계 자체에 있었다. 스토커를 없애고, **설비
> `simpy.Resource`의 대기열 길이를 그대로 스토커 점유량으로** 쓰도록 바꾸자(OHT가 드롭오프 전에
> 대기열 길이를 확인해 꽉 차 있으면 기다림) 큐 길이가 부하/차량 수/버퍼 크기에 따라 실제로
> 달라지기 시작했다. 겉으로는 잘 도는 시뮬레이션이라도 핵심 지표가 늘 상수로 나온다면 의심해봐야
> 한다는 걸 새삼 확인한 경험.

**디스패칭 정책 비교** (차량 5대, FOUP 10개 × 1바퀴, 동일 시드로 공정 비교):

| 정책 | 평균 반송 시간 | P95 반송 시간 | 평균 가동률 |
|---|---|---|---|
| 최근접 차량 | **91.4초** | 197.8초 | 0.047 |
| 구역기반 | 115.7초 | 270.5초 | 0.060 |
| FCFS (위치 무시) | 175.1초 | 306.9초 | 0.089 |
| 예측 기반(적응형) | 91.4초 | 197.8초 | 0.047 |

위치를 고려하는 정책(최근접/구역기반)이 FCFS보다 뚜렷이 짧다. 예측 기반 정책은 이 부하 수준에서 예측 지연이 "혼잡" 임계값을 넘지 않아 매번 최근접을 선택했다 — 틀린 게 아니라, 낮은 부하에서는 정교한 전환이 필요 없다고 올바르게 판단한 것으로 읽힌다. 아래 §5의 발견(피처 중요도 1위가 실시간 부하)과 일관된 결과: 지금 이 시나리오는 그 실시간 부하 자체가 낮다.

**차량 대수 민감도** (최근접 배정 고정): 2대(239초) → 4대(102초) → 6대(76초)로 가파르게 줄다가, 6대→8대(76→65초) 이후로는 8대→10대가 거의 그대로(65→64초)다. **6~8대 구간에서 한계효용이 꺾인다** — 이후엔 차량을 늘려도 스테이션 처리 시간 자체가 병목이라 반송 시간이 거의 안 줄어든다.

**스토커 용량 민감도** (차량 4대 고정): 용량 1(98.6초) < 용량 2(102.4초) = 용량 3 = 용량 5(102.4초) — **작은 버퍼일수록 평균 반송 시간이 오히려 짧다.** 버퍼가 작으면 back-pressure가 일찍 걸려 시스템에 동시에 떠 있는 FOUP 수(WIP)가 자연히 눌리는데, 이게 개별 FOUP 입장에서는 리드타임 단축으로 이어진다 — 린 생산에서 "WIP를 줄이면 리드타임이 준다"는 원리가 그대로 재현된 셈이다. 최대 큐 길이는 반대로 버퍼가 클수록 커지는데(용량 1→3, 용량 5→4), 이는 버퍼가 클수록 더 크게 쌓일 "여유"를 주기 때문이라 당연한 결과이지 흥미로운 신호는 아니다.

**예지보전 피드백** (§6의 모델을 시뮬레이션에 실제로 연결, 15개 시드 평균 — 예지보전 프로세스가 소비하는 난수 때문에 단일 시드 비교는 왜곡될 수 있어 여러 시드로 평균냈다): 예지보전 없음 82.3초 vs 적용 87.8초로, **차량이 주기적으로 고장 나 운행 중단되면 평균 반송 시간이 약 6.7% 나빠진다.** `docs/AMHS.md` §2에서 말한 "차량 고장 → 정체 도미노"가 실제 수치로 재현된 것.

**Hot Lot(긴급 로트) 우선순위**: 차량이 여유로운 기본 시나리오에서는 hot lot(84.0초)과 일반 lot(83.4초)이 사실상 같다 — 대기 요청이 거의 항상 1개 이하라 우선순위가 재배치할 게 없기 때문이다. 반면 차량 2대·투입 간격 20초로 실제 경쟁 상황을 만들자 hot lot 190.5초 vs 일반 lot 276.5초로 **hot lot이 31% 더 빨랐다**(15시드 평균). 스케줄링 이론의 교과서적인 결과이기도 하다 — **우선순위 규칙은 경쟁(contention)이 있을 때만 의미가 있다.** "긴급 로트 우선 처리 로직을 짰다"고 말할 때, 그게 실제로 효과가 있으려면 시스템이 어느 정도 붐벼야 한다는 전제까지 같이 설명할 수 있어야 한다.

## 5. 반송 지연 예측 (`notebooks/08_amhs_delay_prediction.ipynb`)

차량 대수(3~8대) x 투입 간격(80~220초) 25개 조합으로 시뮬레이션을 반복 실행해 다양한 부하 조건의 반송 로그를 모으고, **반송 요청이 들어온 순간의 정보만으로** 그 반송이 얼마나 걸릴지(회귀) / 지연 위험이 있는지(분류) 예측했다. 검증은 일부 (차량 대수, 투입 간격) 조합 전체를 test로 떼어내는 방식(run-level split)이라, 모델이 본 적 없는 부하 조건에도 통하는지를 본다.

| 지표 | 값 |
|---|---|
| Cycle Time 회귀 MAE | 57.8초 (test 평균 대비 18.8%) |
| Cycle Time 회귀 R² | 0.933 |
| 지연 여부 분류 F1 | 0.947 |
| 지연 여부 분류 AUROC | 0.996 |

**피처 중요도: `concurrent_requests`(요청 시점 시스템 부하) 0.726, `n_vehicles` 0.260, `direct_travel_time`(정적 거리) 0.000.** 즉 반송이 얼마나 걸릴지는 스테이션 간 거리가 아니라 **그 순간 시스템이 얼마나 붐비는가**가 거의 전부 설명한다 — 레이아웃은 고정이지만 부하는 실시간으로 바뀌므로, 실제 MCS도 정적 경로 정보보다 실시간 큐 상태를 보고 판단해야 한다는 뜻으로 읽힌다.

## 6. 차량 예지보전 (`notebooks/09_amhs_predictive_maintenance.ipynb`)

`03_modeling.ipynb`에서 SECOM에 썼던 파이프라인(Isolation Forest + XGBoost 앙상블, 5-fold OOF 임계값 튜닝, SHAP)을 **그대로**, 대상만 OHT 차량 센서(모터 전류, 호이스트 진동, 모터 온도, 브레이크 응답시간, 베어링 온도)로 바꿔 재적용했다.

| 모델 | Precision | Recall | F1 | AUROC |
|---|---|---|---|---|
| Isolation Forest | 0.950 | 1.000 | 0.974 | 1.000 |
| XGBoost | 1.000 | 0.989 | 0.995 | 1.000 |
| Ensemble | 0.950 | 1.000 | 0.974 | 1.000 |

SECOM(F1 0.228)보다 훨씬 높지만, 이건 모델이 더 좋아서가 아니다 — 5개 센서짜리 규칙 기반 합성 데이터가 590개 실측 노이즈 센서보다 근본적으로 쉬운 문제라서다(노트북 05/06과 같은 패턴). 이 노트북의 목적은 수치 자체가 아니라, **SECOM에서 검증한 파이프라인이 도메인을 바꿔도(공정 품질 → 차량 상태) 그대로 재사용된다는 것**을 보이는 데 있다. 이 모델은 노트북에서 평가만 하고 끝나지 않고, `amhs/maintenance.py`를 통해 **노트북 07의 시뮬레이션에도 실제로 연결**했다 — 그 결과는 §4 "예지보전 피드백" 참고.

> 다운스트림이 막히면 정체가 업스트림으로 번지는 back-pressure를 재현했습니다. 그 결과 스토커를 작게 둘수록
> 시스템에 떠 있는 WIP가 줄어 개별 반송의 평균 소요 시간이 오히려 짧아진다는, 린 생산의 원리와 일치하는
> 결과를 확인했습니다.
>
> 디스패칭은 최근접/FCFS/구역기반에 더해, 반송 지연을 실시간으로 예측해 혼잡하면 구역기반으로 전환하는
> 적응형 정책도 만들어 봤습니다. 이 예측 모델은 시뮬레이션 로그로 학습했는데, 피처 중요도를 보면 정적인
> 스테이션 간 거리보다 요청 시점의 실시간 시스템 부하가 지연을 압도적으로 더 잘 설명했습니다 — 그래서
> 실제 MCS도 정적 경로 정보보다 실시간 큐 상태를 기준으로 판단해야 한다는 인사이트를 얻었습니다.
>
> 또한 이상 탐지 프로젝트(SECOM)에서 썼던 Isolation Forest/XGBoost 앙상블을 OHT 차량의 모터·진동 센서 데이터에
> 재적용해 예지보전 모델을 만들고, 이를 노트북 안의 평가로 끝내지 않고 시뮬레이션에 직접 연결했습니다.
> 그 결과 차량이 주기적으로 고장 나 운행 중단되면 평균 반송 시간이 약 6.7% 나빠지는 것을 확인했는데,
> 이는 차량 고장이 반송 정체로 이어지고 그 정체가 인접 구간까지 번지는 AMHS 특유의 리스크를
> 구현으로 직접 보여준 것입니다.
>
> 마지막으로, 실제 fab이 모든 로트를 동등하게 처리하지 않는다는 점을 반영해 hot lot(긴급 로트)
> 우선순위 디스패칭도 구현했습니다. 흥미로웠던 건, 차량이 여유로운 상황에서는 우선순위를 줘도
> 효과가 전혀 없다가, 일부러 차량을 줄이고 반송 요청이 몰리는 경쟁 상황을 만들자 hot lot이 일반
> 로트보다 31% 빨라졌다는 점입니다 — 우선순위 규칙은 자원이 부족해 경쟁이 생길 때만 의미가
> 있다는, 스케줄링 이론의 기본 원리를 시뮬레이션으로 직접 확인한 셈입니다.

## 8. 참고 문헌

이 프로젝트의 디스패칭 정책(최근접/FCFS/구역기반/hot lot/예측 기반)은 직접 설계한 것이지만, 실제 AMHS 연구가 다루는 문제와 어디서 겹치고 어디서 더 나아가는지 확인하려고 관련 문헌을 찾아봤다.

| # | 문헌 | 이 프로젝트와의 관계 |
|---|---|---|
| ① | Agrawal, G., & Heragu, S. (2006). *A Survey of Automated Material Handling Systems in 300-mm Semiconductor Fabs.* IEEE Transactions on Semiconductor Manufacturing, 19(1), 112–120. | AMHS 전반(스토커, OHT, 레이아웃, 디스패칭)의 개념 지도 — §1~3에서 다루는 용어 정리의 근거. |
| ② | Liao, D.-Y., & Wang, C.-N. (2005). *Differentiated preemptive dispatching for automatic materials handling services in 300 mm semiconductor foundry.* The International Journal of Advanced Manufacturing Technology (Springer). | **Hot lot 우선순위 디스패칭**을 다룬 실제 연구(DPD 정책) — 대만 300mm 파운드리 실측 데이터로 검증. `amhs/simulation.py`의 hot lot 구현은 이 논문만큼 정교하진 않지만(전면 선점(preemptive)까지는 안 감, 대기 순서 재배정만 함) 문제의식은 같다. |
| ③ | Wang, C.N., Wang, J.W., Chou, M.T., Liao, R.Y., & Huang, C.J. (2017). *A dispatching method for the lots of different priorities in 450-mm semiconductor manufacturing.* Advances in Mechanical Engineering (SAGE). | 마찬가지로 로트 우선순위 디스패칭 — hot lot이 학계에서도 꾸준히 다뤄지는 실제 문제라는 근거. |
| ④ | Im, S. et al. *Effective overhead hoist transport dispatching based on the Hungarian algorithm for a large semiconductor FAB.* | 이 프로젝트의 최근접/구역기반 정책은 매 순간 그리디(greedy)하게 하나씩 배정하는데, 실제로는 여러 차량-요청 쌍을 전역 최적으로 매칭하는 **헝가리안 알고리즘** 기반 접근이 연구돼 있다 — 다음에 시도해볼 만한 고도화 방향. |
| ⑤ | *Multi-factor OHT scheduling method of AMHS for semiconductor fabrications.* | 거리, 대기시간, 로트 우선순위, 병목 스테이션, 차량 가동률을 함께 고려하는 다변수 스케줄링 — 이 프로젝트가 각각을 별도 정책(최근접=거리, hot lot=우선순위, 예측 기반=혼잡도)으로 나눠 다룬 것을 하나의 비용함수로 통합하면 이 방향에 가까워진다. |
| ⑥ | *Multiagent reinforcement learning-based dispatching model for overhead hoist transfer in AMHS* (2025, ScienceDirect). | 최근 연구는 규칙 기반을 넘어 강화학습으로 가고 있다 — `amhs/predictive.py`(지도학습 회귀로 혼잡도를 예측해 정책을 전환)는 이 방향의 훨씬 단순한 버전이라고 볼 수 있다. |

**솔직한 한계**: 이 프로젝트의 디스패칭 정책은 위 문헌들에 비해 훨씬 단순하다(그리디 배정, 전역 최적화 없음, 학습 기반 정책도 회귀 모델 하나로 임계값만 전환하는 수준). 그럼에도 이 문헌들을 찾아본 이유는 "그럴듯하게 만든 시뮬레이션"이 아니라 "실제로 연구되는 문제를 단순화해서 다뤘다"는 걸 스스로 확인하고, 다음에 더 정교하게 만들 방향(헝가리안 알고리즘, 다변수 비용함수, RL)을 구체적으로 알아두기 위해서다.
